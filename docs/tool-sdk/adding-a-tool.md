# Adding a registered tool

US-219 and US-221 own `@editagent/tool-sdk`. JSON Schema is the argument/result contract (ADR-003); the canonical `Tool` entity and UUIDv7 IDs remain in domain. This batch provides the SDK and adapters, not US-222 editing tools or an agent loop. No production media/AI/render worker operation is advertised by the controlled test worker.

## Registration

Inject a `ToolRegistry` into the composition root. Call `register(manifest, binding)`; no registry/agent switch statement changes. The same logical tool ID/name may have multiple exact semantic versions. A duplicate name/version, conflicting ID/name, unsupported capability or privilege fails at registration. There is no implicit `latest` lookup or hot replacement. Register all implementations before accepting requests.

`ToolManifest` schema version 1 is in `packages/schemas/src/tool-manifest.schema.json`. It includes canonical lowercase UUIDv7 `id`, namespaced `name` (for example `media.inspect`), exact `version`, bounded description, input/output schemas, permissions, capability tags, integer estimated/maximum cost in deployment-defined micro-units, a 1–600,000 ms timeout, `mutating` and named `validationRules`. One micro-unit is a budget accounting unit, not an asserted currency exchange rate.

```ts
import { ToolRegistry, type IAudioTool } from "@editagent/tool-sdk";
const registry = new ToolRegistry();
// manifest is deployment-owned configuration, never supplied by an LLM.
registry.register(manifest, { mode: "in-process", tool: audioTool });
registry.register(remoteManifest, { mode: "remote", target: "media" });
const exact = registry.lookup(manifest.name, manifest.version);
const audio = registry.discover("audio");
const functions = registry.exportFunctions();
```

`IAudioTool`, `IRenderTool`, `IVisionTool` and `ITranscriptionTool` segregate implementations by capability without importing backend framework types. An `ITool.start(input, context)` returns an owned `result` promise plus idempotent asynchronous `cancel()`. Cancellation acknowledges cleanup, not merely cessation of waiting. In-process implementations are **trusted, cooperative code**; they must never block the coordinator synchronously, ignore cancellation or spawn unowned descendants. Use `IsolatedTool` with a **fixed deployment module/export** for CPU-heavy JavaScript. Its bounded-memory Worker is terminated on abort and after result/error; no module identity can come from a call, manifest or queue payload. Worker isolation is not a sandbox for arbitrary code. Native subprocess operations must remain behind their existing supervised adapters and honor the same cleanup contract.

## Schemas and export

The deliberately limited offline JSON Schema 2020-12 subset supports closed objects, bounded strings/arrays, finite numbers/integers, booleans/null, const/enum, required properties, numeric/length/item bounds and conservative patterns. No remote/local `$ref`, custom executable keywords, defaults, coercion, open object maps or arbitrary nested schema constructs. Registering an unsupported schema fails before execution. JSON data is limited to 1 MiB, 100,000 nodes and depth 32; arrays reject holes/accessors, objects reject accessors/classes/prototype-shaped keys, numbers reject NaN/Infinity/unsafe magnitude and strings reject ill-formed UTF-16. AJV errors name JSON-pointer fields and violated rules, without echoing values.

`validationRules` currently supports required numeric field ordering (`start < end`) at the root input/output object. Unknown kinds, missing/optional/non-numeric fields and extra parameters fail. This cross-field constraint cannot be expressed by ordinary JSON Schema: the executor remains authoritative. `exportFunctions()` preserves the exact input schema in a stable provider-neutral function descriptor, plus `x-editagent` metadata containing output schema and relational rules. A provider adapter may select the standard `type`/`function` portion; it must retain the metadata for validation rather than claim model-side enforcement of cross-field rules. Function names encode namespace and exact version; discovery order is stable. No provider-specific structured-output restriction is silently added or discarded.

## Authority and execution

Use `ToolExecutor(registry, authority, audit, dispatcher?, maximumConcurrency?)`. Caller identity comes from authenticated server context, **never model input**; role/grants are not accepted in a call. `PostgresToolAuthority` resolves current account existence, non-deleted project membership and project/asset/timeline ownership. Owner/editor can propose commands or request rendering; viewer can read only. Admin does not imply project membership. Timeline loading is an injected authoritative domain port, not a database implementation invented for this batch.

Only `project.read`, `asset.read`, `analysis.read`, `timeline.propose` and `render.create` are supported. Shell, generic host filesystem, network and asset-write grants are forbidden even when declared. These permissions authorize resource adapters; they are not an OS sandbox for trusted code. Implementations must operate only on `context.resource` and cannot trust a `projectId` from their arguments. Reauthorization occurs at execution, remote consumption and result exposure. Resource revocation cannot roll back arbitrary already-started external side effects; an adapter must use conditional/idempotent commits and cancellation before publishing them.

The executor validates input before calling any implementation, reserves the **maximum** cost atomically before admission, validates output/actual cost before success and enforces a deployment-owned instance concurrency limit (default four, configurable 1–32). A trusted deployment-owned lifetime project budget includes concurrent reservations. Success settles actual cost; failed/cancelled admitted attempts conservatively retain maximum cost. A new billing window/budget increase is an explicit operational decision, not a payload field. Capacity/budget denial is audited without running the tool.

Mutating output must include a bounded nonempty `commands` array. Each command is restored with canonical US-215 `parseCommand`, checked against the authoritative project's timeline and applied to immutable domain values to prove invariants and replayability. IDs must be unique within the proposal. Inserted source assets require separate ownership authorization. The SDK returns **proposals**, never updates a database timeline or original source asset. US-222 owns concrete editing implementations.

## Durable audit and query

Apply the standard API migrations, including `0013_tool_executions.sql`. `PostgresToolAuditRepository` stores schema/version, execution UUIDv7, canonical tool/version, caller/project, input SHA-256, timestamps/duration, sanitized outcome/code, cost and associated job ID. Records contain no raw inputs, outputs, stack traces, credentials or signed URLs. Rejections (including malformed identity), failure, cancellation and timeout are recorded; terminal records cannot be overwritten. Failure to write the admission record prevents execution; failure to write a terminal record prevents a success response. No console log is substituted for durability. An optional nonblocking `onRecord` observer receives the sanitized terminal record; an observational sink failure cannot change the durable outcome. Configure the injected Postgres pool with bounded connection/query/statement deadlines.

Use `executor.record(authenticatedCallerId, executionId)` or `executor.records(authenticatedCallerId, projectId, limit)` (1–100, deterministic descending timestamp/ID order). A caller can query their own denied attempt; other records require current project read authority. Malformed/anonymous attempts are visible only through an authorized project query or the internal operator repository, not an anonymous public route. The repository itself is a trusted infrastructure port; do not expose its raw methods as unauthenticated endpoints. There is no new HTTP API in this batch. A coordinator crash can leave a queryable `running` audit record; operators reconcile it with its durable Job/attempt ledger before changing its terminal outcome. No exactly-once external execution claim.

## Remote dispatch

Inject existing US-129 `enqueueJob`/`cancelJob` functions through `ToolJobLifecycle`, a `JobRepository`, private `PostgresRemoteCallStore` and the audit repository into `QueueToolDispatcher`. No second queue implementation/state machine exists. Fixed type `tool.execute.v1`, queues `tools-media-v1`, `tools-ai-v1`, `tools-render-v1`, Project subject, execution UUID as Job ID, manifest timeout, three attempts and 50 ms exponential backoff. The stable idempotency key binds execution and manifest fingerprint. Queue payload contains only schemaVersion/executionId; private transport rows hold validated arguments and resource identity. Supply secret configuration through reviewed adapters rather than arguments; schemas for media resources must use authorized object IDs, not filesystem paths or signed URLs. Apply normal DB access controls and retention to these private rows.

A worker composition root injects a fixed target `RemoteToolConsumer` and an implementation map into `RemoteToolSupervisor`, then runs existing `runNextJob`. Inject `code => new PermanentJobError(code)` and `() => new JobCancelledError()` to preserve US-129 classification. No job payload can choose code/module/export. The consumer verifies persisted audit/call/manifest identity and hashes, authoritative Project subject, exact version/timeout/target, authority and schema. Unimplemented operations fail explicitly. This batch proves all boundaries with a narrowly scoped real test worker; it does not register fictional production analysis/render tools.

Progress uses existing `JobQueue.publishProgress`/US-130 events, monotonic percentages and attempt identity; no parallel Redis channel. A result is durably stored before Job completion acknowledgment, and retry reuses it after identity/authorization checks. Failed/malformed output is never exposed. On cancellation the dispatcher requests durable queue cancellation and waits for terminal cleanup acknowledgment (bounded five-second watchdog). Unconfirmed cleanup is an error, never a successful cancellation claim. Job ledger/locks remain authoritative under retries/cancel races. Some timeout races end the queue job Failed while others are Cancelled, but the caller audit is timed_out and no result is exposed. A committed Completed job cannot be rewritten as Cancelled. After durable Cancelled, result persistence requires a Running Job and fails closed.

## Verification and risks

`pnpm --filter @editagent/tool-sdk... build`, `pnpm --filter @editagent/tool-sdk test`, and `node --test tests/integration/tool-sdk.integration.test.mjs`. The integration test starts real Postgres/Redis when service URLs are absent; production job ledger, BullMQ, event publisher/subscriber, isolated worker and durable private result/audit tables are exercised. The existing CI root integration suite includes it without a skip.

The SDK executes only reviewed, deployed implementations. Permission declarations do not make untrusted code safe. Schemas can bound JSON, but adapters must additionally enforce backend-specific resources and secret handling. Timeout can terminate owned JavaScript threads; native/child-process adapters must supply supervised cleanup rather than misuse the cooperative interface. Idempotency is at-least-once and result reuse, not universal transactional rollback of external systems. No changes to disabled-Chromium-sandbox compensating controls, US-110 gold, MediaAnalysis versions, US-202 scores, CP2 or Issues #43/#44.
