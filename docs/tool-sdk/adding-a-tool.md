# Adding a registered tool

US-219 and US-221 own `@editagent/tool-sdk`. JSON Schema is the argument/result contract (ADR-003); the canonical `Tool` entity and UUIDv7 IDs remain in domain. This batch provides the SDK and adapters, not US-222 editing tools or an agent loop. No production media/AI/render worker operation is advertised by the controlled test worker.

## Registration

Inject a `ToolRegistry` into the composition root. Call `register(manifest, binding)`; no registry/agent switch statement changes. The same logical tool ID/name may have multiple exact semantic versions. A duplicate name/version, conflicting ID/name, unsupported capability or privilege fails at registration. There is no implicit `latest` lookup or hot replacement. Register all implementations before accepting requests.

`ToolManifest` schema version 1 is in `packages/schemas/src/tool-manifest.schema.json`. It includes canonical lowercase UUIDv7 `id`, namespaced `name` (for example `media.inspect`), exact `version`, bounded description, input/output schemas, permissions, capability tags, integer estimated/maximum cost in deployment-defined micro-units, a 1–600,000 ms timeout, `mutating` and named `validationRules`. One micro-unit is a budget accounting unit, not an asserted currency exchange rate.

```ts
import { ToolRegistry, type IAudioTool } from "@editagent/tool-sdk";
const registry = new ToolRegistry();
// manifest is deployment-owned configuration, never supplied by an LLM.
registry.register(manifest, { mode: "in-process", tool: audioTool });
registry.register(remoteManifest, { mode: "remote", target: "media" });
const exact = registry.lookup(manifest.name, manifest.version);
const audio = registry.discover("audio");
const functions = registry.exportFunctions();
```

`IAudioTool`, `IRenderTool`, `IVisionTool` and `ITranscriptionTool` segregate implementations by capability without importing backend framework types. An `ITool.start(input, context)` returns an owned `result` promise plus idempotent asynchronous `cancel()` and optional independent `forceStop()` escalation. Cancellation acknowledges cleanup, not merely cessation of waiting. In-process implementations are **trusted, cooperative code**; they must never block the coordinator synchronously, ignore cancellation or spawn unowned descendants. Use `IsolatedTool` with a **fixed deployment module/export** for CPU-heavy JavaScript. Its bounded-memory Worker is terminated on abort and after result/error; no module identity can come from a call, manifest or queue payload. Worker isolation is not a sandbox for arbitrary code. Native subprocess operations must remain behind their existing supervised adapters and honor the same cleanup contract.

## Schemas and export

The deliberately limited offline JSON Schema 2020-12 subset supports closed objects, bounded strings/arrays, finite numbers/integers, booleans/null, const/enum, required properties, numeric/length/item bounds and conservative patterns. No remote/local `$ref`, custom executable keywords, defaults, coercion, open object maps or arbitrary nested schema constructs. Registering an unsupported schema fails before execution. JSON data is limited to 1 MiB, 100,000 nodes and depth 32; arrays reject holes/accessors, objects reject accessors/classes/prototype-shaped keys, numbers reject NaN/Infinity/unsafe magnitude and strings reject ill-formed UTF-16. AJV errors name JSON-pointer fields and violated rules, without echoing values.

`validationRules` currently supports required numeric field ordering (`start < end`) at the root input/output object. Unknown kinds, missing/optional/non-numeric fields and extra parameters fail. This cross-field constraint cannot be expressed by ordinary JSON Schema: the executor remains authoritative. `exportFunctions()` preserves the exact input schema in a stable provider-neutral function descriptor, plus `x-editagent` metadata containing output schema and relational rules. A provider adapter may select the standard `type`/`function` portion; it must retain the metadata for validation rather than claim model-side enforcement of cross-field rules. Function names encode namespace and exact version without truncation; registration rejects combinations exceeding the portable 64-character function-name bound. Discovery order is stable. No provider-specific structured-output restriction is silently added or discarded.

## Authority and execution

Use `ToolExecutor(registry, authority, audit, dispatcher?, maximumConcurrency?)`. Caller identity comes from authenticated server context, **never model input**; role/grants are not accepted in a call. `PostgresToolAuthority` resolves current account existence, non-deleted project membership and project/asset/timeline ownership. Owner/editor can propose commands or request rendering; viewer can read only. Admin does not imply project membership. Timeline loading is an injected authoritative domain port, not a database implementation invented for this batch.

Only `project.read`, `asset.read`, `analysis.read`, `timeline.propose` and `render.create` are supported. Shell, generic host filesystem, network and asset-write grants are forbidden even when declared. These permissions authorize resource adapters; they are not an OS sandbox for trusted code. Implementations must operate only on `context.resource` and cannot trust a `projectId` from their arguments. Reauthorization occurs at execution, remote consumption and result exposure. Resource revocation cannot roll back arbitrary already-started external side effects; an adapter must use conditional/idempotent commits and cancellation before publishing them.

The executor validates input before calling any implementation, reserves the **maximum** cost atomically before admission, validates output/actual cost before success and enforces a deployment-owned instance concurrency limit (default four, configurable 1–32). A trusted deployment-owned lifetime project budget includes concurrent reservations. Success settles actual cost; failed/cancelled admitted attempts conservatively retain maximum cost. A new billing window/budget increase is an explicit operational decision, not a payload field. Capacity/budget denial is audited without running the tool.

Mutating output must include a bounded nonempty `commands` array. Each command is restored with canonical US-215 `parseCommand`, checked against the authoritative project's timeline and applied to immutable domain values to prove invariants and replayability. IDs must be unique within the proposal. Inserted source assets require separate ownership authorization. The SDK returns **proposals**, never updates a database timeline or original source asset. US-222 owns concrete editing implementations.

## Durable audit and query

Apply the standard API migrations, including `0013_tool_executions.sql`. `PostgresToolAuditRepository` stores schema/version, execution UUIDv7, canonical tool/version, caller/project, input SHA-256, timestamps/duration, sanitized outcome/code, cost and associated job ID. Records contain no raw inputs, outputs, stack traces, credentials or signed URLs. Rejections (including malformed identity), failure, cancellation and timeout are recorded; terminal records cannot be overwritten. Failure to write the admission record prevents execution; failure to write a terminal record prevents a success response. No console log is substituted for durability. An optional nonblocking `onRecord` observer receives the sanitized terminal record; an observational sink failure cannot change the durable outcome. Configure the injected Postgres pool with bounded connection/query/statement deadlines.

Use `executor.record(authenticatedCallerId, executionId)` or `executor.records(authenticatedCallerId, projectId, limit)` (1–100, deterministic descending timestamp/ID order). Every project-bound record lookup/list requires current project read authority, including the original caller’s denied or successful attempts. Historical execution ownership never authorizes access after membership revocation; the same authenticated session is checked again on every query. Unscoped malformed records are operator-only. Malformed/anonymous attempts are visible only through an authorized project query or the internal operator repository, not an anonymous public route. The repository itself is a trusted infrastructure port; do not expose its raw methods as unauthenticated endpoints. There is no new HTTP API in this batch. At coordinator startup call `await executor.recover()`; new admissions and authorized audit reads also reconcile bounded batches automatically. Recovery uses terminal durable Job state plus the private input/manifest binding and validated cost/output receipt. Queued/Running/Retrying jobs remain running, never guessed failed. Concurrent/repeated reconcilers use compare-and-set terminal audit settlement and one transactional reservation update, so they cannot double-charge or invoke implementations. Recovered duration ends at the durable Job terminal timestamp, not the restart timestamp. Stop intent is persisted before cancellation so an acknowledged timeout remains `timed_out`, even when the Job ends Cancelled. Jobs that Completed without a valid bound result fail closed; Failed/Cancelled jobs never become successful just because a private receipt exists. Known costs use `costBasis=actual`; when no valid cost receipt exists, `costBasis=reserved` explicitly records conservative maximum exposure rather than invented actual cost. A batch contains at most 100 terminal jobs; startup can loop while `recover().length` is nonzero. Database outages fail recovery closed and are retried after recovery; no in-memory log substitutes for durable settlement. In-process executions with no durable Job remain an operator reconciliation concern. No exactly-once external execution claim.

## Remote dispatch

Inject existing US-129 `enqueueJob`/`cancelJob` functions through `ToolJobLifecycle`, a `JobRepository`, private `PostgresRemoteCallStore` and the audit repository into `QueueToolDispatcher`. No second queue implementation/state machine exists. Fixed type `tool.execute.v1`, queues `tools-media-v1`, `tools-ai-v1`, `tools-render-v1`, Project subject, execution UUID as Job ID, manifest timeout, three attempts and 50 ms exponential backoff. The stable idempotency key binds execution and manifest fingerprint. Queue payload contains only schemaVersion/executionId; private transport rows hold validated arguments and resource identity. Supply secret configuration through reviewed adapters rather than arguments; schemas for media resources must use authorized object IDs, not filesystem paths or signed URLs. Apply normal DB access controls and retention to these private rows.

A worker composition root injects a fixed target `RemoteToolConsumer` and an implementation map into `RemoteToolSupervisor`, then runs existing `runNextJob`. Inject `code => new PermanentJobError(code)` and `() => new JobCancelledError()` to preserve US-129 classification. No job payload can choose code/module/export. The consumer verifies persisted audit/call/manifest identity and hashes, authoritative Project subject, exact version/timeout/target, authority and schema. Unimplemented operations fail explicitly. This batch proves all boundaries with a narrowly scoped real test worker; it does not register fictional production analysis/render tools.

Progress uses existing `JobQueue.publishProgress`/US-130 events, monotonic percentages and attempt identity; no parallel Redis channel. A validated result is durably stored after owned-work cleanup acknowledgment and before Job completion acknowledgment, and retry reuses it after identity/authorization checks. Failed/malformed output is never exposed. On cancellation the dispatcher requests durable queue cancellation and waits for terminal cleanup acknowledgment (bounded five-second watchdog). Unconfirmed cleanup is an error, never a successful cancellation claim. Job ledger/locks remain authoritative under retries/cancel races. Some timeout races end the queue job Failed while others are Cancelled, but the caller audit is timed_out and no result is exposed. A committed Completed job cannot be rewritten as Cancelled. After durable Cancelled, result persistence requires a Running Job and fails closed.

## Verification and risks

The integration test starts real Postgres/Redis when service URLs are absent; production job ledger, BullMQ, event publisher/subscriber, isolated worker and durable private result/audit tables are exercised. The existing CI root integration suite includes it without a skip.

The SDK executes only reviewed, deployed implementations. Permission declarations do not make untrusted code safe. Schemas can bound JSON, but adapters must additionally enforce backend-specific resources and secret handling. Timeout can terminate owned JavaScript threads; native/child-process adapters must supply supervised cleanup rather than misuse the cooperative interface. Idempotency is at-least-once and result reuse, not universal transactional rollback of external systems. No changes to disabled-Chromium-sandbox compensating controls, US-110 gold, MediaAnalysis versions, US-202 scores, CP2 or Issues #43/#44.

## QA49 repair: cleanup failures and diagnostics

Required/additional-property diagnostics append the precise property to AJV's escaped JSON Pointer, including nested arrays. Only field locations and rule names are exposed; input values never appear.

Execution outcome and cleanup outcome are separate. Cleanup is bounded by the existing five-second watchdog, followed by one independent owned escalation (or one idempotent retry). `IsolatedTool.forceStop()` terminates that exact Worker; remote escalation requests cancellation of that exact Job and awaits its durable terminal acknowledgment. A cleanup exception never bypasses audit settlement or replaces the primary execution failure. A valid result is not published when cleanup is unconfirmed. `cleanupStatus=failed`/`cleanupCode=cleanup_unconfirmed` remains durable and queryable, even when the primary outcome is cancelled, timed_out or invalid_output. Such a record explicitly requires operator attention; it is not a claim that resources stopped. Raw adapter exceptions/causes, credentials and paths are neither returned nor stored in audit/job failure reasons. Sanitized execution ID, primary code and cleanup code support correlation with protected infrastructure logs.

Focused proof uses real PostgreSQL/BullMQ and separate coordinator processes: eleven SIGKILL stages (including an uncommitted settlement transaction), two barrier-synchronized recovering coordinators, repeat reconciliation and reservation invariance. It also injects cleanup rejection into the actual isolated Worker path, verifies forced termination, and checks member revocation/role changes using the same authenticated caller context.

## QA49 publication, deadline and cleanup recovery

Apply `0015_tool_publication_outbox.sql` before admitting Tool jobs. A database trigger commits each `tool.execute.v1` Job and its `tool_job_publications` intent atomically, using the canonical US-129 Job insertion path. Admission requires its bound private call, running audit and unexpired deadline. The outbox stores the stable Job ID and absolute deadline; the authoritative Job supplies the publication envelope. No raw executable payload or new queue protocol is introduced.

At startup run `executor.recover()` and schedule it periodically while the coordinator is serving. New admissions and authorized reads also recover. Recovery claims up to four pending publications with `FOR UPDATE SKIP LOCKED` and a one-second lease, so a crashed publisher loses its claim. Publication has a one-second observation bound; unresolved intents remain recoverable. The same BullMQ Job ID/idempotency key is reused, including after ambiguous Redis acknowledgments. Retry is at-least-once publication, not exactly-once external side effects. A recovery batch may publish work without finalizing an audit: do not use the returned terminal-record count as proof the entire outbox is drained. Continue periodic recovery until work completes or its deadline expires.

The manifest timeout now includes audit admission, authorization, publication, queue waiting and remote execution, measured from the durable audit start. The dispatcher returns owned work before Redis I/O. Stop intent and the queued/retrying Job fence are persisted in PostgreSQL before best-effort Redis cancellation. Deadline-expired queued work is cancelled on recovery. A stale worker save cannot resurrect a terminal Tool Job. The consumer checks the absolute deadline and polls durable stop intent independently of Redis, using its combined AbortSignal for owned inference and Redis checks. Late publication can remain in BullMQ but cannot authorize execution or successful result persistence. Cleanup grace remains bounded separately; temporary transport failures do not extend the logical execution deadline. Configure bounded PostgreSQL pool/statement deadlines; a total database outage cannot guarantee immediate durable settlement and requires recovery after database availability returns.

Private transport rows now record independent cleanup acknowledgment. Before owned work starts, the receipt is `unconfirmed`; `succeeded` or `failed` is written only from the actual cleanup result. A cleanup-note SQL error never replaces a primary `invalid_output` or changes its permanent retry classification. Terminal audit settlement uses that private acknowledgment, not an inference from Job completion. Work that never started records `not_required`. If the receipt write itself fails, `unconfirmed` remains queryable; recovery can update that field only from a subsequently acknowledged durable cleanup fact, without changing primary outcome, duration or cost. It never invents success from the absence of a process or from a terminal Job alone. If both the observer and its acknowledgment are lost, cleanup stays unconfirmed and requires independent resource verification.

Real-service fault tests: `node --test tests/integration/tool-sdk-publication-recovery.test.mjs`. They SIGKILL a separate coordinator at the PostgreSQL-commit/Redis-publication boundary, recover with concurrent fresh OS processes, pause/resume dedicated real Redis for admission timeout/cancellation/late publication, and reject cleanup writes with real PostgreSQL triggers. Existing F1–F4, authorization and isolated Worker regressions remain in `tool-sdk.integration.test.mjs`.

Fault-test infrastructure provisioning uses a separate bounded setup hook so a cold patched-image build is not charged to the fault-test budget. The fault suite retains its 90-second deadline, ten-second handshake watchdogs and 2,000 ms execution-deadline assertions (under 3,500 ms including bounded settlement). Teardown attempts every owned service and reports failures.

### Admission leases and diagnostic trust boundaries

Migration `0016_tool_admission_leases.sql` commits a non-renewable admission lease with every execution audit, before recovery, authorization or reservation. The lease binds an internal coordinator UUID, the registered execution mode and the absolute manifest deadline. PostgreSQL rejects changes to managed lease identity. Reservation and attachment check ownership, stop intent, terminal state and expiry. Job insertion/outbox creation locks that same audit and checks the deadline; an expired coordinator cannot resurrect work by completing a delayed insert.

Recovery includes job-less admissions, not only terminal Jobs. Before the deadline it leaves a legitimate admission alone; after expiry it takes a SKIP LOCKED audit claim and independently rechecks durable Job existence. A remote implementation cannot start before durable Job creation, so a proven job-less remote admission settles to `timed_out` (or its recorded cancellation), with the unused reservation reduced to zero in the same transaction. A killed recovery transaction rolls back both audit and budget changes. Repeated/concurrent recovery uses terminal CAS accounting. An existing outbox-bound Job with an interrupted historical attachment is linked only from matching durable private identity and then follows authoritative Job-state/receipt reconciliation. A cancelled Job with zero attempts, no result and `not_required` cleanup likewise proves unused exposure; other admitted failures retain conservative reserved exposure unless a validated cost receipt exists. No result is fabricated.

Expired pre-lease records are upgraded only from the deployment's trusted registered name/version and timeout, not caller input. Active pre-lease records are not changed before that declared deadline. Unknown historical implementations cannot be assumed to have had no effects: they retain conservative exposure and unconfirmed cleanup. In-process executions also retain exposure when effects cannot be disproved. PostgreSQL availability is required for durable settlement; recovery resumes after an outage. The lease is a deadline fence, not a heartbeat claiming that a dead process can be identified before expiry.

The terminal Tool Job SQL fence returns zero affected rows on a rejected stale state transition. The canonical repository's existing void `save` API preserves its compatibility; `recordCompletion` rejects a fenced write and rolls back the associated attempt instead of reporting a fabricated completion. Non-Tool Job behavior is unchanged.

Field diagnostics include trusted schema property names (escaped JSON Pointer segments) and array indices. Caller-controlled extra keys are represented by `[additional-property]` at their trusted parent path, never echoed. Input values, raw adapter errors and stacks are not included in SDK errors, audit records or record-event sinks. Trusted schema names remain actionable, including required-property diagnostics.

Run `node --test tests/integration/tool-sdk-admission-recovery.test.mjs` for real PostgreSQL/Redis/BullMQ admission SIGKILL and full-budget recovery, transaction rollback, concurrent fresh coordinators, publication/attachment fences, truthful accounting and sanitized diagnostics. The 2,000 ms logical execution deadline is unchanged; the new multi-scenario suite has its own bounded harness budget. Existing publication, cleanup, revocation, queue and schema regressions remain mandatory.
