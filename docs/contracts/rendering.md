# Rendering: US-216 and US-217

The render queue is `render-remotion-v1`; jobs have type `render.remotion` and a canonical project subject. `publishRenderJob` validates the typed payload, checks the actor's owner/editor membership in an active project, and uses the existing US-129 durable job and BullMQ lifecycle. The payload cannot supply an output key, URL, source code, module path, or executable. The versioned JSON Schema belongs to `packages/schemas`.

## Worker isolation and the Owner exception

Issue [#45](https://github.com/mahmoudemad68/Your_Editor/issues/45) records the Owner's approval of Remotion's disabled Chromium sandbox **for this batch only**. Non-root execution does not enable Chromium sandboxing. Remotion 4.0.534 launches Chrome Headless Shell 157.0.8080.0 with `--no-sandbox` and `--disable-setuid-sandbox`; no renderer fork or modified dependency is used. This is an accepted residual risk, not a claim of browser sandbox protection.

The runtime is split into a credentialed coordinator and a credential-free browser executor. Each pair processes one job at a time. The executor has `network_mode: none`, including no bridge interface, route to storage, public network, or metadata endpoint. Its only HTTP server is loopback and serves an allowlisted immutable bundle and verified staged files. The coordinator is on an internal network to Postgres, Redis and S3. No port is publicly exposed by either service.

Both services use UID/GID 10001, a read-only root, Docker's default seccomp filter, `no-new-privileges`, all capabilities dropped, an init reaper, and explicit CPU/memory/PID/open-file/file-size limits. The executor verifies its actual Linux process, cgroup, mount and network settings at startup and refuses to start without them. Shared scratch/control volumes are bounded tmpfs named volumes, not host filesystem binds. There is no Docker socket, host PID/network namespace, privileged mode, or SYS_ADMIN capability. `/tmp` is bounded, non-executable tmpfs; scratch/control tmpfs mounts also use nosuid/nodev/noexec. Swap is disabled for both services. Persistent output belongs in S3; scratch volumes are intentionally ephemeral and not an archive.

A compromised browser still shares the container kernel and can access its own staged job assets. Container isolation cannot eliminate kernel/runtime vulnerabilities. Deploy one coordinator/executor pair per isolation boundary; do not share a scratch/control pair among independently scaling coordinators. Production network/firewall policy must preserve the internal coordinator network and the executor's absence of egress. Do not weaken these settings to make a runtime start.

## Bundle and output identity

The image build bundles the compiled, registered compositions exactly once. A deterministic sorted file/content digest identifies that bundle as `renderVersion`; the catalog records the invocation count. Jobs reuse the immutable bundle, and runtime bundling/download is absent. A failed bundle fails the image build. A new bundle produces a new version. A worker admits only its installed version; deployments must drain or route outstanding old-version jobs to their matching pair rather than silently reinterpret them. The browser archive is acquired at image build from the exact official Remotion URL and verified with a pinned SHA-256.

Outputs are H.264/yuv420p MP4 at `renders/<renderVersion>/<project UUID>/<job UUID>.mp4`. The key is constructed internally from canonical identifiers. Before upload, the canonical media-core FFprobe adapter verifies the MP4 container, stream, codec, dimensions, exact rational rate, duration and nonempty size. A full decode through media-core verifies the exact frame count; the discarded verification encode never replaces the uploaded artifact. Duration tolerance is half a composition frame; expected duration is calculated once with integer rational arithmetic. Uploads are conditional on absence, and metadata binds the canonical input fingerprint and output checksum/size. Retries can deep-download, verify and reuse an existing matching output. This is at-least-once execution with idempotent side effects, not exactly-once rendering.

## Progress, deadline and cleanup

Remotion's frame callbacks report rendered/encoded/total frames on the private control socket. The supervisor maps bounded monotonic render progress to the existing US-130 `mix` stage, reserving 100% for validated, uploaded output. US-130 coalesces intermediate updates; the worker does not create another event protocol or Redis channel. Attempt identity is preserved by the existing event contract.

The default worker concurrency is one and internal Remotion concurrency is two (validated range 1–4). Their product bounds concurrent frame work; the composition is bounded to 30 minutes, 1–60 fps, at most 108,000 frames and the admitted pixel budget. The job envelope controls cancellation/timeout. A separate executor watchdog limits work if the coordinator disappears. Remotion's per-frame `delayRender` timeout is 30 seconds. Worker job timeout defaults to 300 seconds and is configurable up to 600 seconds; this is an execution bound, not a promise that every 30-minute input finishes in it.

Each job gets an internal random scratch directory and a fixed compiled child module. Cancellation closes the control request and propagates to Remotion. The parent tracks descendant PID/start-time identities, including detached Chromium processes, and escalates termination only within that owned tree. Cancellation is not acknowledged until the executor confirms cleanup. Unconfirmed cleanup makes the executor unready and fails closed. Abort during upload removes the matching owned output. Scratch is removed after success, failure and abort; stale scratch from crashes is reclaimed at startup and after a bounded idle age. SIGTERM/SIGINT stop consumption and abort active work before closing queue, database and health resources.

It writes MP4/evidence under ignored `.local/render-batch`, and tears down its containers, network and tmpfs volumes. A sufficiently long render is cancelled after observing actual Chromium processes; PID/start-time identities are checked independently afterwards. Fast package tests cover admission, configuration, identifiers and progress. Rendering artifacts never enter git.

US-110 render-success rate counts admitted logical jobs, not queue retries. Cancellation and intentional timeout/error probes are reported separately from the five-second acceptance render. The generated evaluation baseline, independent human accuracy limitation and CP2 status are unchanged by this batch.

## Timeline composition and registered components

`TimelineV1` takes the existing `TimelineSnapshot` (referenced from the canonical project schema), a background, a caption style, and a bounded array of component bindings. The project subject in the durable job is authoritative: a snapshot for another project is rejected. `FixtureV1` remains the separate minimal typed-props composition. Both are compile-time registrations; a payload cannot load another module or provide React/JavaScript source.

The mapper restores the canonical domain value before creating a frame plan. For rate `N/D`, the absolute frame clock is `roundHalfUp(frame * 1,000,000 * D / N)` microseconds, matching ADR-008/domain frame snapping. A clip occupies the frames whose clock is in its half-open timeline interval. Each boundary independently uses the first frame with a clock greater than or equal to that boundary. This also correctly inverts rounded timestamps such as 66,667 us at 30 fps; applying a naive ceiling to that value would introduce a one-frame error. No durations accumulate floating-point time. The supported Remotion `ffmpegOverride` hook replaces the SDK's approximate encoder framerate with the admitted rational `N/D`, and pins MP4 video timescale to `N` during both pre-encoding and stream-copy stitching. Each frame is exactly `D` video ticks. This avoids the one-tick rescaling error observed with the SDK's default 90,000 timescale; output validation compares rates by integer cross multiplication. No dependency source is patched, and a payload cannot supply encoder arguments. Sub-frame clips with no visible frame fail admission. Composition duration is quantized to this same clock, with less than one frame of terminal background possible.

Media playback is 1:1. The source offset is `inPoint + firstVisibleFrameUs - timelineStartUs`; only at the Remotion API boundary is this bounded integer/rational offset converted to a possibly fractional frame value. `Sequence` supplies placement/duration; `OffthreadVideo`, `Audio`, and `Img` receive only verified local bundle asset identities. Existing track order is layer order, with later tracks above earlier tracks. Media uses contain scaling; gaps use the explicit background. Audio gains combine in dB and clamp to the supported -60..12 dB range; opacity effects multiply. Opacity has no audible effect, and gain has no effect on captions/graphics. This defines renderer behavior without changing the domain's deferred property-applicability policy.

Cuts retain touching half-open boundaries. Because the canonical domain has adjacent, exclusive clips, a visual dissolve holds the outgoing clip's last visible frame during the incoming clip's initial transition window and fades the incoming visual above it. The held visual is muted; audio retains the exact cut/1:1 timing. The transition never extends source reads or shifts timeline boundaries. This is a visual dissolve, not an audio crossfade or a change to canonical transition semantics.

The component factory admits `solid-v1` (hex background) and `title-v1` (bounded literal Unicode text, colors and font size). Caption tracks use the registered caption layout with bounded color/font/direction fields. React renders text literally; no HTML injection, URL, CSS object, arbitrary font, executable module or unknown component is accepted. Missing/duplicate bindings and malformed text fail before Chromium starts. Renderer admission is 128 sources, 64 tracks, 2,048 clips, 128 component bindings, 1,000 UTF-16 code units per caption and 200 per title. These are worker resource budgets, not changes to project-domain limits.

## Constrained asset resolution

Issue #45 permits equivalent constrained storage access in place of browser-visible signed URLs. The coordinator resolves source IDs from the durable job's active project and requires uploaded, inspected, validated MediaAssets with matching kind, duration, content hash and validation hash. Storage keys must equal the canonical `projects/<project UUID>/media/sha256/<content hash>` identity. It does not accept URLs, presigned URLs, caller keys or filesystem paths. Authorized source bytes are streamed from configured private S3 into an exclusive scratch file, checked against exact SHA-256 and size, and exposed to the executor only as `<sha256>.<allowed extension>`. Total input bytes are capped at 512 MiB; the executor independently checks the staged identity, scope, regular-file status, realpath, size and hash before browser launch.

The credential-free renderer serves only these verified files over its private loopback bundle server. There is no remote fetch/proxy endpoint. It has no route to S3 or the public network, so Chromium/OffthreadVideo cannot use media URLs for SSRF. Local routes expire when the per-job server and scratch close. Input identities are included in the output fingerprint, and retry reuse still checks current asset authorization. No signed URLs or credentials persist in job data. The US-122 database currently admits video uploads; audio tracks can use their audio streams. Image/audio MIME support in the resolver does not add an ingestion API or change US-122's allowed upload types.

OffthreadVideo threads are bounded to two; decoded media caches are explicitly 128 MiB each. The executor's cgroups additionally bound aggregate browser/compositor use. Remotion itself also supplies `--disable-dev-shm-usage` in its supported launch implementation; this worker does not add it. A 1 GiB `/dev/shm` is still explicitly configured, and any SDK use of `/tmp` stays within its 2 GiB tmpfs limit. These are observed SDK behaviors, not claims that a Chromium sandbox is enabled.

This differs from the historical US-106 Remotion 4.0.532 / React 18.3.1 benchmark; those historical measurements are unchanged. The existing hardened media-worker FFmpeg 7.1.5 build recipe supplies FFmpeg/FFprobe validation. Remotion's own pinned compositor/encoder is an SDK-internal dependency; application FFmpeg execution still goes through media-core.

The exact installed Remotion 4.0.534 `LICENSE.md` grants free use to individuals, nonprofits, evaluation, and for-profit organizations with up to three employees; larger for-profit organizations need a Company License. The recorded individual Owner/project arrangement is eligible for implementation/evaluation. Reassess eligibility before commercial use if the legal entity changes. This is not an MIT license, and no paid Company License purchase is claimed.

The Linux x64/glibc native compositor is an explicit pinned optional dependency, and image construction verifies it is present. Browser and bundle acquisition happen at build time. Runtime images omit bundler/dev dependencies and unused global npm/corepack tools. No inference, Timeline editing, US-201/204/210 implementation, US-218 strategy, or follow-up Issues #43/#44 repair is included.

These configuration and dry-run tests do not deploy a release.
